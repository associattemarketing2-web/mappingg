# Mappingg WhatsApp gateway (QR-linked numbers)

Holds the WhatsApp connections behind **s-admin → Communication → WhatsApp Inbox**.
A number is linked like WhatsApp Web (scan a QR, or type an 8-character code);
its new messages, and the recent chats the phone shares when linking, are saved
to the same Postgres database the website uses.

> **Not the official WhatsApp Business API.** It uses Baileys (the WhatsApp Web
> protocol). WhatsApp can restrict or ban numbers that look automated. Keep it
> for normal one-to-one chats; do bulk / marketing sends from the official
> whatapi.in number (s-admin → WhatsApp).

## How it runs

It is part of the website project — one repo root, one `package.json`, one
deploy. `npm run start` (scripts/start.mjs) starts the Next.js site on `$PORT`
and this gateway on `127.0.0.1:8099` (`WA_GATEWAY_PORT`), and points the site
at it. The gateway port is never public; only the site on the same server calls it.

Each linked number keeps a socket open 24/7, so the server must **never sleep**:
Render Starter plan or above, or any VPS running `npm run start` (e.g. under pm2).
**Not Vercel** — Vercel stops the code after each request.
Only **one** copy may run at a time (a lease row in `wl_gateway_lease` enforces
it, so a redeploy waits for the old copy to stop instead of fighting over logins).

## Site on Vercel → gateway on Railway

Vercel can't keep the WhatsApp connections open, so the gateway runs as a
separate always-on service built from this same repo (root directory `./`):

1. railway.com → New Project → Deploy from GitHub repo → this repo (root `./`).
2. Service → Settings → Deploy → **Custom Start Command**: `npm run start:gateway`.
   Replicas: **1**.
3. Service → Variables (only these — don't paste the whole `.env`, and **no `WA_GATEWAY_PORT`**):
   `DATABASE_URL`, `WA_GATEWAY_SECRET`, `WA_GATEWAY_KEY` (same values as the site's `.env`).
4. Settings → Networking → **Generate Domain**. Check `https://<domain>/health` → `{"ok":true,…}`.
5. Vercel → the site → Settings → Environment Variables: `WA_GATEWAY_URL=https://<domain>`
   and the same `WA_GATEWAY_SECRET`; remove `WA_GATEWAY_KEY` / `WA_GATEWAY_PORT` there. Redeploy.

While this runs, `npm run dev` on a computer whose `.env` points `WA_GATEWAY_URL` at
localhost takes the numbers over; the server gets them back when it stops.

## Deploy on Render

`render.yaml` already has everything (plan `starter`, 1 instance). Add on the
service's Environment tab, besides the website's own variables:

| Name | Value |
|---|---|
| `DATABASE_URL` | same as the website (already there) |
| `WA_GATEWAY_SECRET` | generated by Render from `render.yaml` |
| `WA_GATEWAY_KEY` | the **same** value as in your `.env`. **Keep it; changing it logs every number out.** |

Do **not** set `WA_GATEWAY_URL` on the server — `npm run start` sets it.
Without `WA_GATEWAY_SECRET`/`WA_GATEWAY_KEY` the site still starts; only the
WhatsApp Inbox says "not set up".

## Deploy on a VPS

```sh
git clone … && cd mappingg && npm ci && npm run build
# .env with the site's variables + WA_GATEWAY_SECRET + WA_GATEWAY_KEY
pm2 start npm --name mappingg -- run start
```

## What is stored (Postgres)

| Table | What |
|---|---|
| `wl_accounts` | one row per linked number: label, phone, status, who linked it, team access |
| `wl_auth` | WhatsApp login keys, **AES-256-GCM encrypted** with `WA_GATEWAY_KEY` |
| `wl_chats` | chat list per number (name, last message, unread, assigned teammate) |
| `wl_messages` | messages per number; `raw` (media keys for downloading files) is encrypted |

Every row carries `account_id`; the website only shows a number's chats to the
super admin, the person who linked it, teammates added to it, or the teammate a
chat is assigned to.

## Limits (WhatsApp's, not ours)

- Old chats: only what the phone shares when linking (usually recent chats); no full history.
- The phone must open WhatsApp at least once every ~14 days or the link expires (status "Logged out").
- Up to 4 linked devices per WhatsApp account; this uses one.
- Files are fetched from WhatsApp when opened; very old ones may no longer be available.

## Local run

`npm run dev` at the repo root starts it too when `.env` has
`WA_GATEWAY_URL=http://localhost:8099` (it takes the numbers over from the
live server while it runs). `npm run test:gateway` runs its tests.
